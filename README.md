# 积分兑换 · Points Exchange

一个可运行的 Web App：用户完成任务获得积分，再用积分兑换数字商品。其中三种商品（`ebook` / `theme` / `course`）的兑换码由外部 API 发放，另外两种是站内虚拟权益。

技术栈：**TypeScript · Fastify · React (Vite) · PostgreSQL（`pg` + 原生 SQL）· Vitest**

---

## 快速开始

需要 **Node.js 22.12+**（推荐 22 或 24 LTS）、**pnpm**，以及一个 **PostgreSQL 14+**（用下面任一方式启动）。

没有 pnpm 的话：`corepack enable`（Node 22/24 自带）或 `npm i -g pnpm`。

### 1. 启动 PostgreSQL

**方式 A：Docker**

```bash
docker compose up -d --wait     # --wait 会等 Postgres 就绪；本机 5432 已被占用时请先停掉本地 Postgres
```

**方式 B：本机安装（macOS / Homebrew）**

```bash
brew install postgresql@16
brew services start postgresql@16
```

### 2. 配置环境变量

```bash
cp .env.example .env
```

然后编辑 `.env`：

| 变量 | 说明 |
|---|---|
| `DATABASE_URL` | 开发库连接串。Docker 用默认值即可；**Homebrew 安装没有 `postgres` 用户**，要改成 `postgres://<你的系统用户名>@localhost:5432/points_exchange` |
| `TEST_DATABASE_URL` | 测试库，**库名必须以 `_test` 结尾**（测试会清空它）。Homebrew 用户同样要改用户名 |
| `DIGITAL_GOODS_BASE_URL` | 外部 API 地址，默认 `https://digital-goods-api.vercel.app` |
| `DIGITAL_GOODS_API_KEY` | 外部 API Key，**只放 `.env`，不要提交** |
| `PORT` / `WEB_PORT` | 后端端口（默认 3000）/ 前端开发端口（默认 5173） |
| `COOKIE_SECURE` | 部署在 HTTPS 下时设为 `true` |

### 3. 安装依赖并初始化数据库

```bash
pnpm install
pnpm db:setup      # 数据库不存在会自动创建 → 执行迁移 → 写入演示数据（可重复执行）
```

### 4. 启动

```bash
pnpm dev           # 后端 :3000 + 前端 :5173，打开 http://localhost:5173
```

> **需要代理才能访问外网？** Node 内置的 `fetch` 默认不读 `HTTPS_PROXY`。启动脚本已加上 `NODE_USE_ENV_PROXY=1`（Node ≥ 22.21 支持），只要在环境里设置了 `HTTPS_PROXY`，服务端就会走代理访问外部 API；没有设置代理则没有任何影响。

生产模式（单进程同时托管前端）：

```bash
pnpm build
pnpm start         # 打开 http://localhost:3000
```

## 功能范围

- **用户**：注册、登录、退出（用户名 + 密码，scrypt 哈希，服务端 session + httpOnly cookie）。所有查询都按当前用户过滤，别人的订单返回 404。
- **任务**：3 个每日任务（每个 UTC 日可领一次）、3 个新手任务（每个账户一次）。点击即完成。
- **商城**：3 个外部兑换码商品 + 2 个站内权益。积分不足时按钮置灰并提示差额。
- **兑换记录**：状态（处理中 / 已发放 / 已退款）、兑换码（可复制）、处理中订单的原因和下次重试时间，页面自动轮询刷新。
- **积分明细**：每一笔变动及变动后余额。

## 关键设计与取舍

### 1. 余额 = 余额列 + 只追加的流水表

`users.balance` 保存当前余额，`point_ledger` 记录每一次变动。两者**永远在同一个事务里**通过唯一入口 `applyPoints()` 更新。

- 读余额只需一次主键查询，不用每次汇总流水。
- 流水能完整回答「这些分从哪来、到哪去」，并且可以随时核对：`balance == SUM(ledger.delta)`。测试在每个用例结束后都会检查这一点。
- 数据库约束兜底，代码写错也不会产生脏账：`CHECK (balance >= 0)` 保证不会透支；部分唯一索引保证**每个订单最多扣一次分、最多退一次分**，每次任务完成最多发一次奖励。

### 2. 并发：锁用户行 + 数据库唯一约束

- **兑换**：事务内先 `SELECT … FOR UPDATE` 锁住用户行，同一用户的兑换请求会在这里排队，「查幂等键 → 查余额 → 建单 → 扣分」不会交错执行。所以并发请求不会让余额被扣过头，也不会重复建单。
- **任务领取**：`task_completions` 上有唯一约束 `(user_id, task_id, period)`，用 `INSERT … ON CONFLICT DO NOTHING` 判断是否已领。不需要先查再写，并发点击也只会成功一次。
- **防双击 / 重发**：前端打开兑换弹窗时生成一个幂等键，`(user_id, idempotency_key)` 唯一。同一次确认不管点了几次、网络失败后重试几次，都只会生成一个订单。

### 3. 外部 API：先扣分，再调用；结果不确定时绝不退款

订单号（如 `ord_mfx…`）直接用作外部 API 的 `requestId`。外部 API 保证同一 `requestId` 的重试会返回原来的码，所以**我们这边任何重试都不会导致重复发码**。

流程：

1. **事务**：锁用户 → 校验余额 → 建单（`processing`）+ 扣分
2. **事务外**：同步调用外部 API，最多等 8 秒
3. 按结果分类处理（`server/external/digitalGoods.ts` 的 `classifyResponse`）：

| 外部返回 | 判定 | 处理 |
|---|---|---|
| 200 且响应体正确（同一 requestId、同一商品、有码） | 已发码 | 保存码 → `delivered` |
| 400 / 413 / 422 | **确定没有生成码** | `failed` + 退款（同一事务）。若之前有过结果不确定的 POST，先 GET 确认外部确实没有这笔，再退款 |
| 超时 / 断网 / 5xx / 200 但响应体异常 | **不知道有没有生成码** | 保持 `processing`，**不退款**，后台按指数退避重试；计入「不确定次数」 |
| 401 / 429 | 确定没生成码，但只是暂时被拒 | 保持 `processing`，按退避（429 还看 `Retry-After`）重试；**不计入**「不确定次数」 |
| 409 | 这个编号在外部已有记录（且商品不同） | 视同不确定，不退款；GET 拿到的记录商品对不上时也不会误当成功 |

4. **后台补发**：服务进程内每 3 秒扫描一次到期的 `processing` 订单，用同一个 `requestId` 重新 POST。退避间隔 5s → 10s → … → 最长 10 分钟；遇到 429 时按 `Retry-After` 等待，并停止本轮。认领订单时就会先把下次重试时间推后一个退避周期，进程中途崩溃也不会过早重试。
5. **放弃的条件**：结果不确定的 POST 累计 8 次（含同步那一次）仍没有结论，就不再 POST，改用 `GET /deliveries/:id` 确认：
   - 查到码 → 补记为已发放（这种情况是之前的响应丢了）
   - **明确返回 404** → 这时才标记失败并退款
   - GET 也失败 → 继续挂起，稍后再查

这套流程保证了：
- **不会「码发了分没扣」**：扣分发生在调用外部 API 之前。
- **不会「退了分码却发了」**：只有在外部明确表示没发码时才退款。
- **不丢码**：结果不确定的订单会一直重试或查询，直到拿到确定答案。
- **页面如实反映状态**：处理中的订单会显示原因（超时 / 服务故障 / 限流……）、已尝试次数和下次重试时间。

**为什么 401 / 429 也挂起而不退款**：这两种情况下，请求在鉴权或限流阶段就被拒绝了，基本可以确定没有发码，所以退款在一致性上是安全的。选择挂起是业务上的考虑：它们都是暂时性的，Key 过期是我们自己的配置问题，限流过一会儿就会解除。挂起后换上新 Key 或等限流解除，订单会自动完成，用户不用重新兑换。代价是这段时间里用户的积分一直被占用，页面会如实显示原因。

因此，判断一个结果怎么处理，要同时看两个问题：**确定没发码吗？重试有可能成功吗？** 只有「确定没发码，且重试也不会成功」（400 / 413 / 422）才退款；只要不确定是否发了码，就绝不退款。

**租约（lease）而不是长事务**：调用外部 API 前，先用一条条件 `UPDATE` 认领订单（`lease_until`），然后在事务外发起 HTTP 调用。这样同步请求和后台 worker 不会同时处理同一笔订单，也不会在等外部响应的那几秒里一直占着数据库连接和行锁。租约过期会自动释放，进程崩溃后订单也能被重新接手。

### 4. 为什么选这套技术栈

- **Fastify + React (Vite)，而不是 Next.js**：后台补发需要一个常驻进程定时执行，放在 Fastify 进程里很自然。前后端职责清楚，后端可以直接连真实 Postgres 做集成测试。
- **`pg` + 原生 SQL，而不是 ORM**：这个项目的正确性依赖 `FOR UPDATE`、`ON CONFLICT`、条件 UPDATE、部分唯一索引这些数据库特性，写成原生 SQL 可读性最好，评审一眼就能看出锁和约束在哪。迁移就是 `server/db/migrations/*.sql`。
- **不引入队列 / Redis**：补发任务存在 `orders` 表里（`next_attempt_at` / `lease_until`），Postgres 本身就是可靠的队列，少一个组件就少一个一致性问题。

### 5. 其他细节

- 每日任务按 **UTC 日**刷新，与外部 API 的日额度重置时间一致。
- 下单时保存价格快照（`orders.price`），之后商品调价不影响已有订单的扣分和退款金额。
- 站内权益在建单事务里直接标记为已发放，不调用外部 API。
- session 表只存 token 的 sha256，数据库泄露也拿不到可用的 cookie。

## 我如何验证

`pnpm test` 会连接真实的 PostgreSQL 测试库，外部 API 换成 `scripts/fakeGoodsServer.ts`。这个假服务按 API 文档实现了幂等、409、404，并且可以为每个请求注入故障。

- **对账不变量**（`test/helpers.ts` 的 `assertInvariants`，通过 `afterEach` 在每个用例结束后自动执行）
  - 每个用户：余额 = 流水之和
  - 每个订单：恰好扣一次分；失败订单恰好退一次，其余订单不退
  - 和外部对账：外部生成的每个码，我们都有对应订单；已发放订单的码与外部一致；已退款订单在外部一定没有码
- **并发**：10 个兑换并发、余额只够 3 个 → 恰好成功 3 个；同一幂等键并发 5 次 → 1 个订单；同一任务并发领取 10 次 → 只发 1 次奖励；同一订单被 5 个 worker 同时处理 → 只有 1 次外部调用
- **外部故障**：422、503、超时（但码已生成）、500（码已生成但响应丢失）、连接被拒、响应体异常、429 + Retry-After、401 持续很久后恢复（不消耗 POST 预算、不退款）、重试时收到 422（外部有码 → 补记发放；外部没码 → 退款）、达到不确定次数上限后 GET 返回 404 / 返回码 / 继续失败、同步调用中途进程异常后由后台接手、退款函数重复调用只退一次，以及多用户并发 + 随机故障的混合场景
- **HTTP 层**：未登录 401、注册送分、重名、错误密码、跨用户访问订单返回 404、积分不足 422、退出后 session 失效
- **手动验证真实 API**（只发了个位数的请求，**没有任何压测**）：开发时第一次兑换恰好遇到网络问题，本地看到的是超时或网络错误，但外部其实已经生成了码。订单一直停在「处理中」，没有退款。网络恢复后，后台用同一个 `requestId` 重试，拿回的是**同一个兑换码**，最终标记为已发放。这正好从真实环境验证了「结果不确定不退款、重试不重复发码、不丢码」这条设计。

## 已知问题与可改进之处

- **理论上的竞态**：放弃前的 GET 确认，距离上一次 POST 至少隔了一个退避周期（分钟级）。如果外部服务把一个早已超时的请求拖到那之后才处理完，GET 可能返回 404，而码随后才生成。实际概率极低，而且当前 API 没有「取消请求」的能力，无法完全排除。
- 后台补发在 Web 进程内运行。多实例部署时租约能保证不会重复处理，但如果要做更大规模，应该拆成独立的 worker 进程。
- 挂起时间很长的订单（例如 Key 过期、每日或总额度耗尽后的 429）会一直等待，积分一直被占用。页面会展示原因，但没有运营告警和人工处理入口（题目不要求）。按 API 文档，额度耗尽后等待并不会恢复，这类订单需要人工介入。
- 没有登录限流、验证码、找回密码（题目不要求）。
- 站内权益目前只记录为「已生效」，没有做实际的展示效果（比如头像框）。
- 每日任务按 UTC 日刷新（与外部 API 的额度日界一致），国内用户会在早上 8 点看到刷新；如需按北京时间，只需改 `periodFor` 一个函数。
